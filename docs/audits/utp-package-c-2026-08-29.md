# УТП — пакет C — строгий AI-контракт и evidence guardrails

Дата: 2026-08-29

Статус: завершён

## Реализовано

- Добавлена строгая Zod-схема `UtpAiResult` с полями `usp`, `usedEvidence` и
  `missingData`; лишние поля и невалидный JSON отклоняются на backend.
- Workflow разделены на `strategy.utp.generate` и `strategy.utp.improve`, при
  этом оба используют существующий action code `utp` и его серверную цену.
- Оба prompt config используют один `UtpFoundation`, семь внутренних проверок
  качества, естественный текст длиной 500–1200 символов и JSON-only ответ.
- Frontend читает только типизированный `structured` результат и больше не
  извлекает УТП из raw-текста или регулярных выражений.
- `usedEvidence` проверяется по точным source refs, section key и label из
  текущего `UtpFoundation`; неизвестные и межпроектные ссылки отклоняются.
- `missingData` должен точно соответствовать отсутствующим секциям foundation,
  включая безопасный `editPath`.

## Evidence guardrails

- Все числа в УТП должны присутствовать в реально использованных источниках.
- Срок подтверждается числом с той же единицей измерения: например,
  «30 клиентов» не подтверждает «за 30 дней».
- Заявления об опыте и образовании требуют соответствующих фактов профиля.
- Клиентские результаты требуют ready-кейса.
- Гарантии, абсолютные обещания, лидерство и эксклюзивность допускаются только
  при наличии соответствующего proof evidence.
- Невалидный результат получает один ограниченный repair attempt. Если он снова
  не проходит проверку, артефакт не сохраняется и зарезервированные AI-баллы
  освобождаются.

## Billing и совместимость

- Validation retry происходит внутри одной операции и не создаёт второго
  списания.
- Сохраняются существующие idempotency и reserve/finalize/fail механизмы.
- Frontend не подставляет fallback-цену: показывает серверную quote и фактическое
  `aiPointsCharged`, когда списание состоялось.
- Каноническое хранение УТП и production-данные не изменялись.
